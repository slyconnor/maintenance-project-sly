V5.1 — RECOMMENDED CLOUDFLARE DEPLOYMENT (EXISTING WORKER + GITHUB)
==================================================================

This guide is designed around the existing Cloudflare Worker named:

  maintenance

and the existing D1 database named:

  maintenance-project-sly-db

WHY GITHUB / WORKERS BUILDS?
----------------------------
Your current Cloudflare project is Workers Static Assets. A full-stack Worker
needs an actual Worker entry point plus an assets configuration. Cloudflare
Workers Builds can connect an EXISTING Worker to a GitHub/GitLab repository and
run `npx wrangler deploy` whenever the repository changes.

Cloudflare documentation:
https://developers.cloudflare.com/workers/ci-cd/builds/
https://developers.cloudflare.com/workers/static-assets/

STEP 1 — FIND THE D1 DATABASE UUID
----------------------------------
In Cloudflare:

  Workers & Pages -> D1 -> maintenance-project-sly-db

Open the database and copy its Database ID / UUID.

Do not use the database name in place of the UUID.

STEP 2 — PUT THIS PROJECT IN A PRIVATE GIT REPOSITORY
-----------------------------------------------------
Create a private repository such as:

  maintenance-project-sly

The repository ROOT must contain:

  package.json
  wrangler.jsonc
  src/
  public/
  migrations/

Do not put an extra folder around those files.

STEP 3 — EDIT wrangler.jsonc ONCE
---------------------------------
Replace:

  PASTE_D1_DATABASE_UUID_HERE

with the UUID copied in Step 1.

Do not change:

  "name": "maintenance"

Cloudflare requires the Wrangler Worker name to match the existing Worker when
connecting a repository to an existing Worker.

STEP 4 — CONNECT THE EXISTING WORKER TO GITHUB
----------------------------------------------
Cloudflare:

  Workers & Pages
  -> maintenance
  -> Settings
  -> Builds
  -> Connect
  -> GitHub
  -> choose the repository

Use the production branch (normally main).

Build command:
  Leave blank (there is no front-end compile step).

Deploy command:
  npx wrangler deploy

The package contains Wrangler as a dev dependency, and the Wrangler config is
already present, so Cloudflare should not need to auto-detect the project.

STEP 5 — CHECK THE FIRST BUILD
------------------------------
The build should deploy:

  src/index.js        as the Worker runtime
  public/*            as Static Assets
  DB                  as the D1 binding from wrangler.jsonc

The existing custom domain / Access setup is deliberately not listed as a route
inside wrangler.jsonc. `workers_dev` is false so routing/custom-domain management
can remain in the Cloudflare dashboard.

STEP 6 — ADD THE ADMIN EMAIL RUNTIME VARIABLE
---------------------------------------------
After the real Worker runtime has deployed, Cloudflare should allow Runtime
Variables.

Go to:

  maintenance -> Settings -> Variables and Secrets

Add a normal text variable:

  Name:  ADMIN_EMAILS
  Value: <your approved admin email>

Multiple admins can be comma-separated later, for example:

  admin1@example.com,admin2@example.com

The config uses `keep_vars: true` so dashboard-managed runtime variables are not
intentionally overwritten by future Wrangler deployments.

STEP 7 — TEST THE BACKEND
-------------------------
Sign in through Cloudflare Access, then open:

  https://maintenance.project-sly.uk/api/health

A healthy response should contain roughly:

  "version": "5.1.0"
  "database": { "bound": true, "ready": true }
  "adminEmailsConfigured": true

For an OTP engineer it should show a normal user identity.
For your Cloudflare login it should show:

  "cloudflareLogin": true
  "admin": true

STEP 8 — TEST THE USER FLOWS
----------------------------
ENGINEER:
  maintenance.project-sly.uk
  -> One-time PIN
  -> All Jobs dashboard
  -> can add/edit jobs

ADMIN:
  maintenance.project-sly.uk
  -> choose Cloudflare login
  -> approved ADMIN_EMAILS match
  -> Worker redirects to /admin.html

ADMIN DASHBOARD VIEW:
  /index.html?view=dashboard

This special query lets an authenticated admin inspect the ordinary All Jobs
screen without being immediately redirected back to Admin.

RASPBERRY PI:
  /pi.html

Keep the separate read-only machine/service-token Access setup for the Pi. The
Pi page reads the same D1 state but exposes no edit controls.

DATABASE TABLE CREATION
-----------------------
V5.1 creates its small D1 schema automatically when the API is first used.
You do not need to run the migration manually for first deployment.

The migrations/0001_initial.sql file is retained so future database changes can
be managed with formal D1 migrations.
